# RV-M3.3-001 — First end-to-end unattended demonstration

**Status:** BLOCKED — governed live route, commissioned worker and verified knowledge provider are absent
**Roadmap cursor:** M3.3 remains the earliest unaccepted step. This checkpoint does not accept or waive it.
**Environment:** Camrui; shared database `riverview` / `riverview_dev`
**M3.2 dependency:** technical commissioning evidence at source `0fd10357ccdf2c9a0c87ba4a6f41e37ecff33ce9`; M3.2 full DoD remains open.

## Required proof

Roadmap M3.3 requires reproducible Camrui evidence for authorized concurrent
assignments, worker execution, independent verification, restart/recovery,
dashboard and notification. It explicitly makes this the first meaningful
runtime milestone. Tests or scripts alone cannot pass it.

## Preflight findings

The following findings describe the original M3.3 preflight; the current
implementation delta is recorded in the dated follow-up below.

1. The live shared ledger has one previously completed M3.1 worker assignment;
   it does not establish concurrent unattended work. Existing M2 tests verify
   concurrency and recovery only in isolated PostgreSQL schemas.
2. `PostgresWorkerAdapter` checks that a worker's free-form `scope_ref` string
   equals an assignment's `authority_ref`. The worker contract explicitly says
   the registration/control-plane operation is trusted and does not validate
   that reference against a durable Steward grant. No live grant service is
   connected to assignment creation or worker dispatch.
3. `ContinuousWorker` defaults to `UnavailableKnowledgeProvider`. The only
   packaged v1 provider is a test mock. A real source-backed institutional
   provider is not available in the deployed runtime. The fail-closed worker
   therefore cannot claim verified grounding/preflight from that missing
   provider.
4. The shared application DB role owns the schema. A library-level authorization
   check alone cannot prevent a service using that same role from inserting
   grants or assignments directly.

These are implementation/security boundaries, not SSH or operator convenience
issues. No shared assignments, workers, grants, credentials, or service state
were modified to manufacture the demonstration. The previous M3.1 live worker
evidence and M3.2 notification commissioning remain intact.

## Resolution path

- Implement M4.1 institutional identities and exact grants with a database
  privilege boundary; connect verified grants to assignment creation and worker
  registration/claim before shared assignments are authorized.
- Implement or integrate a real source-backed knowledge provider and bind its
  version/hash evidence to the exact deterministic work contract. No missing,
  mocked, or unverified retrieval may authorize an action.
- Resume M3.3 with two explicitly authorized concurrent assignments, distinct
  real workers, durable artifacts and independent verifiers; exercise restart,
  recovery, dashboard and notification against the same live run.

M3.3 remains IN PROGRESS and no milestone acceptance is claimed.

## 2026-10-11 UTC — RV-M4.1-GRANT-ENFORCEMENT follow-up

Worker registration and worker action authorization now use the dedicated
authority SQL function in isolated tests. `PostgresWorkerAdapter` requires the
exact `worker.register` grant on registration and re-checks exact
`assignment.execute` / `assignment.verify` action and scope for claims, starts,
execution, result commit and verification. Credential/grant revocation fails
closed. The protected SQL function, role privileges and actual worker operations
passed 22/22 focused PostgreSQL boundary, worker and CME integration tests on a
disposable PostgreSQL 16.15 cluster; see the M4.1 revision record and the
committed checkout evidence.

Camrui migration 0002 and the exact function-only runtime ACL are now applied
after a fresh protected backup/restore rehearsal, from the exact CI-passing
source commit. A rollback-only live role transaction verified exact grant
allow, wrong action deny, direct table denial, and manager function denial; all
synthetic rows were rolled back. Evidence is
`evidence/checkouts/M4.1-DB-BOUNDARY/20261011T090700Z-live-exact-grant/`.
The application worker adapter is not deployed. A new isolated
`AuthorizedAssignmentIntake` path now requires the exact `assignment.create`
grant and holds the grant-row lock across ledger assignment/event persistence
in the same PostgreSQL transaction. Its PostgreSQL integration tests cover
authorized attribution, idempotent replay, wrong/missing/revoked grants,
authority unavailability, and caller-supplied actor rejection. This is an
application library boundary only: low-level `PostgresLedger.create` remains a
persistence primitive, no live route/service is wired to the intake, and the
shared runtime role is not restricted from direct ledger writes. No commissioned
real worker service exists, and the real repository-backed institutional
knowledge provider remains unavailable. Therefore no authorized live M3.3
end-to-end run can yet be asserted. M3.3 remains BLOCKED on those operational
service/provider conditions, not on isolated assignment-intake code. Evidence
is recorded in `evidence/checkouts/M3.3-ASSIGNMENT-INTAKE/`. Next: integrate the
authorized intake into the governed request path, package/deploy the worker
adapter through the controlled service path, and continue independent provider
work.

## 2026-10-11 UTC — RV-M3.3-ASSIGNMENT-INTAKE

Implemented `AuthorizedAssignmentIntake` as a fail-closed application entry
point. It derives actor identity from the exact-grant function result and
performs the ledger write within the same outer transaction that holds the
grant-row lock. Isolated PostgreSQL tests passed 4/4 against disposable
PostgreSQL 16.15. The test schema was removed. This does not make raw ledger
writes safe for application callers; routes must use the authorized entry point,
and no route or live worker service is currently commissioned.
