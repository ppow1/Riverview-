## Intake and scope

Roadmap acceptance requires a Linux-supervised event processor with a durable
outbox/inbox or equivalent persisted cursor, event replay, and resumable
assignment progression. Acceptance requires that a new assignment advances with
no chat/UI turn, restart resumes unfinished work, and duplicate events are
idempotent. The M1.2 migration is deployed and the existing M1.1 service remains
healthy. This task is initially isolated to code and disposable PostgreSQL test
schemas; it does not deploy a service or change the commissioned database/runtime.

The processor will consume `assignment.created` events in sequence, use a
persisted consumer cursor, and advance newly queued assignments to `ready` using
the existing idempotent ledger transition API. The transition's deterministic
key includes the source event ID. If a process stops after committing a
transition but before cursor advancement, replay returns the prior semantic
transition and then advances the cursor. The cursor update occurs only after
event handling succeeds. PostgreSQL advisory locking in the long-running service
prevents two active copies of the same consumer; durable row locking serializes
checkpoint updates.

The worker executes no external effects and claims no worker scheduling, fairness,
leases, independent result verification, CME monitoring, dashboard or
notifications. Failures remain visible in structured logs; retry uses bounded
backoff. The first version has one ordered cursor, so a poison event may delay
later events; M1.4 scheduling/fencing and M2 failure isolation remain separate.
Database credentials are not accepted in command arguments or logged. The DSN
contains identity/location only and libpq obtains the password through a protected
passfile.

## Design, records and acceptance tests

- Migration for the cursor is separately scoped under the event-processor
  component; it is not added to the deployed M1.2 migration set.
- Processor functions are repeatable and callable in one-shot test mode; the
  deployed entry point runs continuously and handles SIGTERM safely.
- A crash-window test applies a transition without committing the cursor, then
  recreates the processor and proves semantic replay, one transition event, and
  cursor advancement.
- A restart test confirms persisted cursor and subsequent new assignment
  progression. A repeated processing test proves duplicate events do not create
  duplicate transition rows.
- Tests run only against disposable PostgreSQL schemas on an isolated test
  cluster. Shared `riverview_dev` receives no M1.3 DDL or rows.
- Process graph `rv:event-processor:assignment-progression` is authored with the
  implementation and generated flow view in the same change.
