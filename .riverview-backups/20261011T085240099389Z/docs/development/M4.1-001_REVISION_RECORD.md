**Roadmap criterion:** persistent institutional identity, grants and delegated authority; office role separated from occupant, implementation and state; restart and occupant replacement preserve continuity; unauthorized actions rejected.

## Design and current implementation

The new `institutional_authority` package and additive migration define durable
principals and hashed bearer credentials; exact action/scope grants; credential
and grant issue/revocation; office roles; occupant and model/tool implementation
identities; append-only authority events; and office-keyed state with bounded
compare-and-swap writes. Occupant replacement increments a binding revision,
revokes the old occupant's exact office-state grant in the same transaction, and
preserves office state. The first Steward bootstrap is restricted to a trusted
root-local call and can occur only once. Subsequent administrative changes
require a live Steward credential and exact management grants.

**Implementation limitation:** the feature is not integrated into worker
registration, assignment intake, dashboard actions, or any live service. The
current shared DB application identity owns tables; a process with that owner
credential can bypass library checks with SQL. The migration remains unapplied
to `riverview_dev`. Applying it or creating live worker assignments before
database-role separation would not establish the required security boundary.

### Isolated database privilege boundary addition

The dry-run-first provisioner protects the nine M4.1 authority tables and
append-only trigger function under a `NOLOGIN` table owner. A security review
found the earlier manager membership in that owner role was broader than needed:
it allowed DDL and could bypass registry/append-only controls. The corrected
contract requires a dedicated schema containing only the authority tables,
`schema_migrations`, and the trigger function; rejects unrelated relations and
functions; revokes schema visibility from `PUBLIC` and the ordinary runtime;
and grants the `NOINHERIT`, no-membership manager only `USAGE` plus
`SELECT`/`INSERT`/`UPDATE`/`DELETE` on the nine registry tables. It cannot
create/drop objects, execute the trigger function directly, or assume the owner
role. The manager remains a trusted capability because direct DML can bypass
application-level grant checks; it must not be delivered to ordinary worker,
CME, event-processor, or dashboard runtimes.

This is isolated engineering only. The shared Camrui schema remains owned by
`riverview_core`; the helper refuses to provision it. No ownership transfer,
role/credential, migration, identity, grant, worker or assignment was changed
in the shared database. Live commissioning still requires an approved distinct
schema-owner/migration identity, protected manager-credential delivery and
service integration and compatibility verification of the existing application paths. A protected backup and disposable restore rehearsal passed on 2026-10-11; this does not constitute shared-schema commissioning.
