# Riverview V2 Living Roadmap

The first V2 roadmap view is a read-only presentation over the committed V2 development roadmap, Issue #268 evidence, and the canonical Parking Lot / Ready Bench documents in `ppow1/Riverview`. The planning summaries and source links are a curated UI index, not an execution registry. Parking Lot, Steward-approved elaboration, Design/Specification, Ready Bench, Active Work, and Complete are distinct lanes; where a board is not integrated, the view links to its authoritative source and reports that limitation.

Grace Autonomy and Website Visualization are the primary workstreams. Grace's supervisory loop is not polled or represented as live. Current objective state is fetched on demand from the existing authenticated `/api/v1/auth/session` and `/api/v1/objectives?limit=25` endpoints, only for identities whose existing account role includes Steward. Live objective cards expose the API's lifecycle status/stage, assignment state, exact assignment link, latest event and timestamp, verification decision, current rework rationale, and update time. Blocked/waiting records with no source reason explicitly say the reason is unavailable. The projection does not expose dependency edges, a canonical workstream, or priority; the view does not infer any of them.

The current host's configured PostgreSQL schema (`riverview_dev`) contains the Dashboard objective and assignment projections but does not contain `roadmap_items` or `roadmap_revisions`; there is no installed Dashboard route for the separate canonical master-roadmap store. Therefore the live objective API is authoritative for current operational objective records only, not for roadmap waypoints. UI labels distinguish verified live objective data from documented roadmap intent/delivery evidence. If the live read fails, retained cards are labelled stale. Canonical roadmap dependency/lifecycle status remains unavailable until an existing authorized API/database connection is provided; no Git snapshot is treated as live state.

The original Riverview master-roadmap code documents PostgreSQL as the live status authority, but V2 has no route to that store. Its README also says Ready Bench is intentionally empty while `boards/ready_bench.md` lists RB-0001 as READY. The UI reports this conflict and does not treat the board text or Git JSON as live execution state. P0–P3 on curated V2 entries are display priorities derived from Current/Now/Next/Later ordering; source board priorities outside that scale remain unassigned and retain their original label.

Keyword, tag, and priority filters plus native `<details>` disclosures are client-side. There are no promotion, priority-write, or execution controls because no corresponding existing authorized API is integrated in this view. Promoting an idea remains a Steward decision under `ppow1/Riverview/docs/operations/PARKING_LOT_AND_READY_BENCH.md`; Ready Bench presence does not authorize execution.
