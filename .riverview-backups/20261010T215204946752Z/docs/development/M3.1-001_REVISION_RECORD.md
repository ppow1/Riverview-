## Requirements and design

1. Project the canonical PostgreSQL ledger, M2.4 CME health/attention and available worker/verifier tables; never create a parallel status database.
2. Bind the browser and versioned JSON API to one authenticated application origin. GET-only API, loopback-only listener, bounded read-only DB queries and privacy filtering prevent UI authority or private payload leakage.
3. Display workflow state, persisted last progress, attempts, verifier summaries, durable event/correlation/causation IDs, CME/worker freshness, migration/source/deployment provenance and diagnosis references. Missing tables/heartbeats stay not-initialized/unknown; stale/unavailable never show green.
4. Render shell first; keep navigation local and cached, load details lazily, and refresh bounded status/event pages separately. No tab switch calls inference or reconstructs institutional state.
5. Export a redacted server snapshot with browser-local bounded error/navigation telemetry; no credentials, payloads or unrestricted conversations.
6. Keep resident chat, explicit conversation-to-work-order promotion, contextual commands, resource registry and capability management as compatible future interfaces, not M3.1 implementations. Issue #13's read-only dashboard is explicitly only an intermediate foundation.
