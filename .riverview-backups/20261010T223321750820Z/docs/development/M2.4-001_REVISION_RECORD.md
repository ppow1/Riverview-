# RV-M2.4-001 — CME monitoring service

**Classification:** New component

**Working branch:** `codex/m2.4-cme-monitor`  
**Target:** Camrui development host, isolated PostgreSQL 16.15 cluster  
**Execution model:** Continuous scheduled polling with durable restart re-scan  
**Authority boundary:** Read assignment/lease/worker state; write CME-owned metadata/events only; no worker dispatch, assignment mutation, or recovery actuation.

## Requirements and acceptance criteria

1. Observe every nonterminal assignment independently, including last meaningful progress and optional deadline.
2. Detect stalls and deadline misses using explicit configured thresholds and durable time/event evidence.
3. Emit idempotent, traceable attention and expired-lease recovery request events without blocking unrelated assignments or directly controlling workers.
4. Report CME heartbeat/freshness and worker health without treating missing worker evidence as healthy.
5. Recover after monitor process termination by reacquiring its database lease, rescanning durable assignments, and avoiding duplicate alerts.
6. Keep the monitor separated from HR, engineering execution, the scheduler, and worker-provider code.

## Design decisions

- Deadline metadata belongs to a CME-owned `cme_assignment_deadlines` table to preserve the existing M1.2 assignment/event migration and contracts. A timezone-aware API validates the assignment before upsert.
- A scan reads all eligible assignments in one ordered query. The latest durable assignment event indicates meaningful progress; worker lease heartbeat is a separate liveness signal.
- Stable event keys bind stall reports to assignment plus progress sequence, deadline reports to assignment plus deadline timestamp, and recovery requests to assignment plus lease generation. `ON CONFLICT DO NOTHING` makes scans and restarts idempotent.
- Recovery requests are records only. The M2.3 recovery coordinator remains the recovery owner; no automatic action is asserted by CME.
- The service holds a PostgreSQL advisory lock while running. Database or scan failures are logged without DSN values and retried with bounded backoff.
