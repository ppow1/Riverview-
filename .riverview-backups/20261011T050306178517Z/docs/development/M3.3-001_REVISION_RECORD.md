# RV-M3.3-001 — First end-to-end unattended demonstration

**Status:** BLOCKED — safe live execution preconditions are absent
**Roadmap cursor:** M3.3 remains the earliest unaccepted step. This checkpoint does not accept or waive it.
**Environment:** Camrui; shared database `riverview` / `riverview_dev`
**M3.2 dependency:** technical commissioning evidence at source `0fd10357ccdf2c9a0c87ba4a6f41e37ecff33ce9`; M3.2 full DoD remains open.

## Required proof

Roadmap M3.3 requires reproducible Camrui evidence for authorized concurrent
assignments, worker execution, independent verification, restart/recovery,
dashboard and notification. It explicitly makes this the first meaningful
runtime milestone. Tests or scripts alone cannot pass it.

## Preflight findings

1. The live shared ledger has one previously completed M3.1 worker assignment;
   it does not establish concurrent unattended work. Existing M2 tests verify
   concurrency and recovery only in isolated PostgreSQL schemas.
2. `PostgresWorkerAdapter` checks that a worker's free-form `scope_ref` string
   equals an assignment's `authority_ref`. The worker contract explicitly says
   the registration/control-plane operation is trusted and does not validate
   that reference against a durable Steward grant. No live grant service is
   connected to assignment creation or worker dispatch.
3. `ContinuousWorker` defaults to `UnavailableKnowledgeProvider`. A real,
   bounded repository-source provider now reads an exact allowlist pinned to a
   commit/package digest and has passed unit and isolated PostgreSQL worker plus
   independent-verifier tests. It is not configured in a live service and is
   not a general institutional knowledge or learning provider; the live worker
   still fails closed until it is deployed and its exact source pin is
   commissioned.
4. The shared application DB role owns the schema. A library-level authorization
   check alone cannot prevent a service using that same role from inserting
   grants or assignments directly.

These are implementation/security boundaries, not SSH or operator convenience
issues. No shared assignments, workers, grants, credentials, or service state
were modified to manufacture the demonstration. The previous M3.1 live worker
evidence and M3.2 notification commissioning remain intact.

## Resolution path

- Implement M4.1 institutional identities and exact grants with a database
  privilege boundary; connect verified grants to assignment creation and worker
  registration/claim before shared assignments are authorized.
- Package and configure the repository-source provider at an exact reviewed
  release commit; bind its returned source hashes to the deterministic work
  contract in the live worker. The provider has no learning store and does not
  replace OctoMiner's real institutional provider. No missing, mocked, or
  unverified retrieval may authorize an action.
- Resume M3.3 with two explicitly authorized concurrent assignments, distinct
  real workers, durable artifacts and independent verifiers; exercise restart,
  recovery, dashboard and notification against the same live run.

M4.1 isolated engineering and M3.3 provider integration engineering are being
pursued as unblockers. M3.3 remains BLOCKED on the live database-enforced
authority boundary and safe authorized live commissioning. No milestone
acceptance is claimed.

## Repository-provider verification checkpoint

The bounded `RepositoryKnowledgeProvider` is implemented at source commit
`59114e1fefcc94c6eacf2f4b25f263c7d627c817`. It is read-only, verifies the
complete fixed worker-contract source set against an exact clean Git commit or
package checksums, and is limited to `deterministic.sha256.v1`. It does not
authorize work and has no learning store.

On Camrui, a socket-only disposable PostgreSQL 16.15 cluster ran the focused
worker cycle. Assignment `worker-cycle-f01da85a9ddf4d7d90ad32ae8148fdde`
persisted attempt `8056c197-d875-460b-b8a4-ba3621795030`, a 98-byte JSON result
with SHA-256
`d4922d9db60d0d3eb68f3d2652532e4b80b9b11471a060817ae5cd274ca9447d`. Grounding,
action preflight, and regrounding returned VERIFIED with complete source
references and commit/hash provenance. A distinct verifier accepted all four
deterministic criteria and the assignment reached `completed`. Learning capture
returned UNAVAILABLE and was recorded honestly. The isolated schema was removed;
the post-suite `rvtest_*` count was zero and the disposable cluster stopped.
The sanitized machine report and command logs are in
`evidence/checkouts/M3.3-REPOSITORY-KNOWLEDGE/20261011T045500Z-59114e1/`.

The full PostgreSQL-backed suite on source commit 59114e1 passed 141/141, with
zero failures, errors, or skips. The provider's eight contract/unit tests and
the focused provider/worker/verifier test passed. Two focused dashboard tests
also passed for readable safe rendering of the new provider cookbook; that test
addition followed the full suite and is checked again by exact-head CI. The
canonical graph check reports 13 workflows and 235 nodes. Final revision audit
and exact-head CI are pending the current documentation/dashboard commit.

No live provider configuration, authority identity/grant, shared database
migration, worker registration, or assignment was created. Accordingly M3.3
remains BLOCKED on database-enforced authority and safe live commissioning; this
is isolated functional integration, not live M3.3 commissioning or institutional
learning.
