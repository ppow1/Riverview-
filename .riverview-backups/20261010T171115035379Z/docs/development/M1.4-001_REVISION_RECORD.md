## Requirement and design

Implement the first M1.4 slice from the roadmap: concurrent independent progress,
fair dispatch, leases and stale-worker fencing. Keep the work isolated from the
commissioned shared schema. M1.3 changes queued assignments to ready; this
scheduler claims ready assignments in age order using `FOR UPDATE SKIP LOCKED`.
An active lease for one assignment does not lock or serialize unrelated ready
assignments. Database-clock expiries and monotonic per-assignment generations
provide fencing. The exact worker and generation must still own an unexpired lease for every
scheduler-authorized transition, including the atomic `ready` to `running` step.
Heartbeat/reclaim/state changes lock assignment rows in one order to prevent a
successful renewal from racing with generation replacement.

M1.4 DDL is isolated in
`src/riverview_core/assignment_scheduler/migrations/0001_assignment_leases.sql`.
It is not included in M1.2/M1.3 migration paths and application code never
applies it implicitly. It has not been applied to `riverview_dev`.

## Initial implementation and verification

`PostgresAssignmentScheduler` implements ordered lease acquisition, heartbeat,
expired-lease reclaim with generation increment, and transactional fenced start
with a causally linked transition event. Three disposable PostgreSQL integration
tests passed on the local isolated PostgreSQL 16.15 UTF-8 cluster:

- An active lease on an older assignment did not block a second worker claiming
  the next assignment.
- Concurrent workers claimed distinct assignments.
- Expired lease reclamation incremented generation; stale start/heartbeat were
  rejected; current generation transitioned exactly once to running.

Exact test log and cleanup evidence will be attached after the complete suite and
checkout gates run. The isolated cluster and unique test schemas are not shared
runtime state. M1.4 has no service deployment or operational acceptance claim.
