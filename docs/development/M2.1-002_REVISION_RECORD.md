## Intake and acceptance intent

Implement a small in-process provider boundary and a repeatable worker cycle so
assignment-local waiting, missing evidence, or action failure cannot halt
independently eligible tasks. Required operations are grounding, action
preflight, regrounding, and learning-event capture. Non-verified provider results
must fail closed and remain durable. This work does not implement institutional
retrieval, learning promotion, a separate service, or a dashboard.

## Design decision

The existing architecture already separates M1.3 intake, M1.4 lease scheduling,
and M2.1 worker execution. The continuous cycle therefore belongs at the worker
boundary and does not change the global scheduler or M1.3 event cursor. Each
cycle claims at most one assignment; `SKIP LOCKED` leases allow concurrent
workers. Non-verified knowledge becomes a durable assignment-local
`blocked`/`WAITING_FOR_EVIDENCE` result, after which later cycles remain
eligible. Infrastructure/database exceptions retry at the worker loop boundary;
durable leases and attempt rows remain the restart/reconciliation source.

The canonical provider types are in
`src/riverview_core/worker_adapter/knowledge_provider_v1/`. Contract `1.0.0`
requires `VERIFIED`, at least one stable source reference, and complete
retrieval before action. Provider exceptions, missing providers and deadlines
are `UNAVAILABLE`; unknown output types are `UNVERIFIED`. Observation rows keep
status, operation, action, references, revision/hash and completeness, not
provider payloads. The five-second default timeout uses bounded daemon threads;
late results are discarded and at most four timed-out calls remain per worker.
Python cannot forcibly cancel a hung in-process provider; providers also need
their own bounded I/O. This limitation is explicit in the handoff contract.
