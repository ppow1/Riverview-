# RV-M3.2-001 — Durable notification and decision requests

**Classification:** New component / institutional integration
**Owner:** Steward Operations / CME integration
**Status:** IN PROGRESS — scoped technical acceptance criteria PASS; full component DoD OPEN
**Working branch:** `codex/m3.2-durable-notifications`, based on M3.1 accepted commissioned branch `codex/m3.1-status-dashboard` at `c8d93bc`; M3.1 PR #16 remains open/draft and is not merged.
**Target:** Camrui PostgreSQL `riverview` / schema `riverview_dev`; authenticated loopback dashboard; dedicated dispatcher service.
**Execution model:** Continuous event-driven/scheduled reconciliation of durable CME attention rows; browser notification rendering and receipt are request-driven.
**Authority boundary:** Dispatcher derives notices and pending review requests from CME/assignment state. Dashboard token proves only possession of the dashboard service credential. Delivery receipt and notification acknowledgment are not Steward identity, approval, assignment mutation, or decision resolution.

## Requirements and scope

- Roadmap M3.2 requires durable attention events, delivery/acknowledgment state, and Steward decision requests, beginning with one tested channel; PASS requires a defined attention condition to reach the tested channel and delivery/acknowledgment outcomes to be truthful.
- Core Contract reserves visual/audio/SMS channels and durable decision requests; M3.2 implements only the dashboard visual channel. No external paid provider is introduced.
- CME remains the authoritative source of attention events. The dispatcher is separate from CME detection, scheduler, workers, HR, and resident reasoning.
- Decision requests are created only for durable assignments currently in `awaiting_steward`. This milestone can notify and record acknowledgment only. Resolution/approval waits for M4.1 institutional identity and authority; no decision endpoint or action is introduced.
- Notifications expose fixed summaries, event/assignment references and timestamps only. Private assignment events and raw CME details are excluded.

## Design decisions

Implemented design: idempotently project CME attention into dedicated durable notification and decision-request tables; expose a bounded authenticated dashboard view; record a delivery receipt after successful visible browser rendering and explicit receipt acknowledgment separately. Both receipts use `authenticated_dashboard_client` provenance and carry no Steward principal claim. Recovery re-scans source rows and relies on unique source-event identities, transaction locking, and bounded batches rather than an in-memory cursor. Receipt events have a database update/delete guard. The API reports dispatcher health as degraded, stale, unverified, healthy, or not initialized based on durable observation.

## Acceptance criteria and verification plan

1. A real persisted CME attention event produces one durable in-app notification; repeated scan/restart creates no duplicate.
2. An `awaiting_steward` assignment produces one durable pending decision request; notification receipt/ack leaves that request pending.
3. Authenticated dashboard browser receives and renders actual notifications; delivery/receipt states advance only after the corresponding successful client request and persist across dispatcher/dashboard restart.
4. Missing migration, unavailable database, unauthorized request, unknown notification, invalid transition, and private-domain assignment fail visibly and do not fabricate successful delivery or approval.
5. One notice/request failure remains local; unrelated CME observation and dashboard service continue.
6. Isolated PostgreSQL tests cover source-event idempotency, concurrent scans, failure/restart recovery, notice state transitions, authority non-effects, and privacy; browser test verifies real route and buttons.
7. Shared deployment requires additive migration preflight, protected backup/restore proof, checksum compatibility, dashboard-only and dispatcher-specific release identity, and post-deployment checks. M1.1/M1.2/M1.3/M2.4 state must remain intact.
8. Full applicable suite, graph synchronization, security, revision audit and GitHub CI pass. Full component DoD is evaluated separately; no Steward acceptance is presumed.
