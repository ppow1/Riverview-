## Requirements and design

Roadmap M2.1 calls for one capability-registered worker with authenticated scope
and durable attempt/result records. Its first deterministic task must be
repeatable, attributable and visible, and worker loss detectable. GPU integration
is explicitly out of scope.

The adapter registers worker identity, capabilities, a scope reference and a
one-time random credential; only the credential SHA-256 digest is stored. The
trusted registration API is not an external grant-validation mechanism. Each
execution requires a registered capability, valid constant-time credential
match, assignment authority reference equal to worker scope, and the exact
current M1.4 lease generation. The only task implementation is a local SHA-256
operation over explicit UTF-8 input. It has no shell, network, arbitrary code,
filesystem or hardware effects.

M2.1 migration `0001_worker_attempts.sql` is isolated from the M1.2/M1.3/M1.4
migration directories and is never applied automatically. It has not been
applied to `riverview_dev`.

## Initial implementation

The adapter creates durable attempt records before deterministic computation,
then rechecks the current fencing token before persisting the result. Attempts
retain worker, assignment, capability, generation, idempotency key, input digest,
status and timestamps. Results store deterministic output plus its digest. Key
reuse with different assignment/worker/generation/capability/input is rejected.
Unfinished attempts are enumerable through `incomplete_attempts()` for worker
loss detection.
