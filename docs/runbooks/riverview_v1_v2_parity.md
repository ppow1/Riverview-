## Evidence and limits

- Live V1 HTML title is “Riverview — Operations”; navigation includes Overview, Assignments, Objectives, Institutional proposals, Grace chat, Resident permissions, Activity, Workflows, Notifications, Documentation, and Account.
- Deployed baseline V2 navigation includes Overview, Residents, Work, Proposals, Living Roadmap, Image Generation, Resources, Knowledge, Communications, and Notification Settings. The migration candidate adds Process Workflows and Documentation. Work contains objective/assignment progress and Engineering Progress; Overview contains Website verification. The V2 Overview cards remain explicitly sample-only; the Residents view is API-backed and keeps source-pinned historical Estate/Jessica references separate from current Riverview authority records.
- V1 bundles reference `/api/v1/account/*`, `/api/v1/notifications`, `/api/v1/events`, `/api/v1/objectives`, `/api/v1/resident-permissions`, and `/api/v1/institutional-proposals`. V2 bundles reference notification settings, snapshot, resident conversation, objective, graph, and status APIs.
- Unauthenticated protected API probes returned 401. This confirms protected routing, not operation-specific authorization or successful authenticated execution for every listed API. The full acceptance runner separately verifies its listed authenticated scenarios.
- Account administration parity includes merged PRs #288–#293. Notification receipt/detail parity includes #303–#305. Grace recovery decision controls and session eligibility gating include #307–#312. Proposal decisions and acceptance baseline corrections include #313–#314; pre-migration production baseline was `RV-WEB-V2-ACCEPTANCE-7eca34b6c6c7`.
- Capability-discovery handoff: V2 exposes the existing proposal `POST` draft, item `PUT` revision, `POST .../decision`, and `POST .../work-orders` operations to a session that passes the existing Steward/institutional authorization checks. No API, executor, registry, or authority rule was added. Registry owner should review those existing operation mappings; the UI screens are not capabilities.
- Dynamic permission catalog: V2 builds its capability and resource inventory from the authenticated `/api/v1/resident-permissions` response backed by `capability_catalog` and `capability_resources`; the website carries no operational capability list. Release declarations are reconciled by the existing C3 authority release process; newly registered enabled records appear after refresh. The active catalog supplies operation IDs, descriptions, authority actions, resources, dependency/approval metadata, and resident effective-policy projection. Input schemas, declaration provenance, executor implementation, availability policy, and authorization contract are rendered when present; this API contract does not guarantee every such field, so V2 labels absent fields unavailable instead of fabricating them. The V2 API does not provide a live executor identity/health observation and returns enabled entries only; disabled/deprecated/removed reasons are not distinguished. The permission store calculates a bounded per-resident effective matrix using the canonical evaluator and matching exact action/resource grants; V2 shows the scope and condition used. V2 labels unmatched resident policy references unavailable and blocks profile editing rather than dropping them. Steward-only profile administration remains on the existing authenticated authority API. Grace's existing `GraceCapabilityRegistry.snapshot()` reads the same canonical catalog and authorized scopes and rechecks exact grants on invocation.
- Capability discovery boundary: `GET /api/v1/capabilities` is the static website page/control inventory, not the operational registry. Worker executor declarations remain in the worker registry. There is no resident-facing website listing endpoint in this release; Grace's existing capability bridge provides her principal-bound view, and other resident exact action/scope/profile checks remain authoritative at invocation. No new executable operation was introduced by the Permissions view increment or the Batch 1 directory/settings/registry surfaces; they reuse the existing authenticated read API and existing writes only. Grace discovery remains through her existing principal-scoped bridge. UI visibility does not confer execution authority. Registry review handoff: no new executor or action was added. The existing C3 declaration gate requires operation identity, input schema, implementation reference, and authorization contract for newly registered dashboard operations; UI screens are not capabilities.
- No V1 functional route remains without a V2 surface after the functional migration increment. Some positive production-browser mutation checks remain skipped because existing reserved test identities have no institutional Steward binding or there is no disposable production objective. Isolated backend tests and the live unauthorised-denial checks preserve the security boundary; no genuine production record was mutated for acceptance.
